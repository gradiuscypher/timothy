# Privacy-forward self-hosted analytics and APM

Research checked against first-party documentation and repositories on **2026-08-03**.

## Recommendation in one minute

For Timothy's current small Docker Compose deployment (React SPA, FastAPI API, one host), the best starting point is:

1. **Umami for product/web analytics**. It is cookie-free by default, has a broad feature set (events, funnels, journeys, retention, goals, UTM/revenue attribution, and Core Web Vitals), uses one PostgreSQL database, and is MIT-licensed. It has the best feature-to-operations balance here. [Umami overview](https://docs.umami.is/docs), [installation](https://docs.umami.is/docs/install), [session/privacy mechanics](https://docs.umami.is/docs/sessions), [license](https://github.com/umami-software/umami/blob/master/LICENSE)
2. **GlitchTip for endpoint and page performance** if the priority is low operational overhead. It groups transactions by endpoint/operation, shows average, p50, p95, count, and errors, and breaks a transaction into spans such as database or outbound HTTP work. It supports the Sentry React and FastAPI SDKs, runs with PostgreSQL and a small application service, and is MIT-licensed. [Performance monitoring](https://glitchtip.com/documentation/performance/), [supported SDKs](https://glitchtip.com/sdkdocs/), [self-hosting requirements](https://glitchtip.com/documentation/install/), [project/license](https://gitlab.com/glitchtip/glitchtip-backend)

Umami v3's Core Web Vitals can identify slow pages as users experience them, but Umami does **not** provide backend request spans or explain whether FastAPI, SQLite, an outbound Discord call, or another operation consumed that time. GlitchTip is the lightweight complement. Choose **SigNoz instead of GlitchTip** when richer Datadog-style RED metrics, database/external-call breakdowns, service maps, trace flamegraphs, dashboards, and latency alerts justify a roughly five-container stack and at least 4 GB of Docker memory.

If browser experience is as important as backend performance, use **OpenObserve instead of GlitchTip**. Its OSS edition combines OpenTelemetry traces with full RUM: Core Web Vitals, page/resource/API timing, JavaScript errors, sessions, and optional replay. It can run as one binary/container locally, though production HA is a larger system and the license is AGPL-3.0. [RUM overview](https://openobserve.ai/docs/user-guide/data-exploration/rum/overview/), [RUM performance views](https://openobserve.ai/docs/user-guide/data-exploration/rum/performance-monitoring/), [self-hosting](https://openobserve.ai/docs/getting-started/), [OSS/enterprise comparison](https://openobserve.ai/downloads/)

These are two different jobs: audience/product analytics answers *who arrived and what they did*; APM/RUM answers *where time and errors occurred*. A RUM tool should not be treated as a complete Google Analytics replacement.

## Practical stack choices

| Goal | Pairing | Why |
| --- | --- | --- |
| **Recommended now: useful, private, light** | **Umami + GlitchTip** | Broad site/product analytics plus slow endpoint/page transactions and errors, while adding only PostgreSQL-backed services. Best match for one React/FastAPI Compose host. |
| **Best end-to-end performance visibility** | **Umami + OpenObserve OSS** | Umami answers traffic/conversion questions; OpenObserve connects browser page/API performance, Core Web Vitals, errors, replay, backend spans, logs, and metrics. Start with replay disabled. |
| **Best backend APM depth** | **Plausible CE or Umami + SigNoz** | Strong service RED metrics, call breakdowns, traces, service maps, dashboards, and alerts. Budget at least 4 GB just for SigNoz and avoid running two ClickHouse-heavy stacks on a small host. |
| **Absolute minimum footprint** | **GoatCounter + GlitchTip** | Deliberately simple analytics and relatively small APM/error stack. Good when funnels/cohorts and full RUM are unnecessary. |
| **Large GA-style marketing requirement** | **Matomo + GlitchTip or SigNoz** | Matomo has the analytics depth, while the second tool handles backend traces. Accepts the highest administration cost. |

## Privacy and rollout guardrails

Self-hosting changes who holds telemetry; it does not make telemetry harmless. APM events can contain route parameters, query strings, request bodies, headers, database statements, user IDs, IP-derived geography, error locals, or Discord identifiers. Recommended defaults:

- Keep observability dashboards private; do not expose them through the public Cloudflare route without a separate access policy.
- Allowlist attributes rather than collecting request/response bodies, authorization headers, cookies, or full query strings.
- Record normalized route templates (for example, `/guilds/{guild_id}`), not raw high-cardinality URLs.
- Use random internal IDs only when user correlation is genuinely needed; never send Discord tokens, session cookies, emails, or display names.
- Start APM traces at **5–10% sampling**, retain them briefly, and increase only for targeted diagnosis. Keep errors at a higher rate if volume permits.
- Leave session replay and user identification off initially. If replay is later justified, mask all inputs, sample narrowly, document the collection, and test the masking against real screens.
- Pin image versions, set retention limits before enabling ingestion, monitor disk growth, and back up only what has a defined retention need.
- Respect analytics opt-out/consent decisions where applicable. Cookie-free or vendor-described “GDPR compliant” behavior is not a universal legal exemption; configuration, URL contents, custom properties, proxy logs, jurisdiction, and purpose still matter.

## Suggested evaluation

Run a short trial before wiring either tool deeply into the application:

1. Deploy **Umami** and either **GlitchTip** (light option) or **OpenObserve** (full RUM option) on a private hostname/network.
2. Instrument only pageviews, a few named product events, React navigation/page transactions, and FastAPI request traces. Do not add identity or replay.
3. Confirm the tools answer four concrete questions: slowest API route by p95; slowest SPA page/navigation; slow database/outbound Discord call inside a request; and page/event conversion path.
4. Inspect the raw captured payloads for secrets and identifiers, then set sampling and retention from measured daily volume.
5. Keep OpenTelemetry at the backend boundary when possible. It preserves the option to move from OpenObserve/SigNoz/Uptrace to another OTLP backend without reinstrumenting the application.
